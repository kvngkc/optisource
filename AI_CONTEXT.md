# Optisource Architecture & Context 

This document serves as the foundational context for understanding the Optisource platform. Read this completely before making any functional changes.

---

## 1. What is Optisource?
Optisource is a multi-tenant B2B Procurement, Inventory, and Sales Management platform explicitly designed for Optical Suppliers and retail Opticians. 

The core problems it solves:
- Intricate inventory management of optical lenses (handling Spherical/Cylinder/Axis/Addition powers and distinct semi-finished lens Base values).
- B2B order placements where Opticians can natively query their Supplier's live database, verify item availability (without seeing raw quantities), and seamlessly submit orders.
- Debt and Transaction management where companies log cash or outstanding debt to unique registered customers.

## 2. Tech Stack Setup
- **Frontend Framework**: React (scaffolded via Vite)
- **Routing**: React Router (`react-router-dom`)
- **Styling**: TailwindCSS
- **Backend/DB/Auth**: Supabase (PostgreSQL, Supabase Storage, Row Level Security)
- **Deployment Structure**: Client-side single page app. All business logic executes directly against the Supabase DB using authenticated REST queries or heavily defined RLS (Row Level Security) policies on the tables.

## 3. Core Database Models
*Note: All core tables are strictly tied to `company_id`. RLS isolates tenants.*
- `companies`: The main root tenant organization.
- `locations`: Physical warehouses/retail front ends belonging to a company.
- `profiles`: Users belonging to a company. Roles include: `super_admin` (system owner), `company_admin` (supplier boss), and `staff` (clerk tied to a specific location).
- `stock` / `transactions`: Handles the literal inventory math. Transactions track both Sales and Inventory Adds.
- `customers` & `debtors`: Links transactions to distinct purchasers. Handles partial payments.
- `optician_orders` & `optician_order_items`: B2B orders generated by external Opticians.
- `order_messages`: Chat interactions tied to an order. Uses the `order-attachments` bucket for payment proof uploads.
- `audit_log`: Heavily logs system activity (Sales, Voids, Auth, Stock imports).

## 4. Optical Specification Formats
Lenses are extremely specific. The system handles standard spherical formats and Base blanks format:
- `sph_cyl`, `sph_add`, `sph_cyl_axis_add`
- SPH, CYL, ADD typically map standard integer numbers to strings (e.g., `+100`, `Plano`, `-075`).
- **Base Handling**: Semi-finished blanks use `base_add` and `base_only`. The system stores them in DB natively as `+100`, `+200` but transparently formats them identically on UI dropdowns as simple `100`, `200`.

## 5. Main Data & UI Workflows

### The Optician Order Workflow
1. A registered Optician arrives at `StockQuery.jsx`.
2. They input a specific Company's `slug` (access code). If the Supplier toggled "Optician Access" ON via Settings, the optician connects.
3. The optician freely queries lens combinations. Availability translates to Checkmarks (stock quantities are legally hidden from competitors).
4. Utilizing the internal LocalStorage Cart, the Optician compiles a batch of lenses and hits Order.
5. The system generates an `optician_orders` row and pings the Supplier. The Supplier reviews it in `OrderDetail.jsx`.
6. Conversations flow in the chat (images upload natively into `order-attachments`).
7. When the Admin hits "Mark Dispatched", they explicitly choose the physical `location`. The system auto-generates `SALE` transactions for every item, dynamically locating and deducting the explicit `stock` amounts under the hood.

### Internal Sales & Debt Collection
1. Staff use `Sales.jsx` to select items. Overselling is natively blocked.
2. If `amount_paid` is less than the `total_amount`, the remaining transforms into a balance in the `debtors` table.
3. Every purchaser requires distinct `name + phone` which queries or binds a unique ID in `customers` table ensuring absolute data integrity.
4. Returns are processed by hovering over Recent Sales and clicking the "Void" option which creates a `SALE_VOID` pushing negative stock values back to `qty`.

## 6. Development Rules & Formatting
- **File Modifying**: Avoid creating new deeply nested state if it belongs in a central database table. 
- **Tailwind**: Adhere to existing stylistic UI paradigms: primarily modern sleek `slate` shades, `rounded-xl` containers, and `inter` typeface logic. Do not insert inline styles unless completely necessary.
- **Tools**: Rely on simple JS array functions and direct Supabase DB queries via the global client in `src/supabase.js`. Do not bring in heavy redundant JS dependencies.
